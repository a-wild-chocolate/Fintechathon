TradeX 五分钟英文演示：操作与排练指南

核心句
客户说“先付一部分”，财务不能直接把发票金额当作回款。TradeX 先确认金额与日期，再更新企业资金预测，最后比较可执行的付款安排。

一、先准备正确的初始状态
当前开发页面可能已经保存了之前的 6,000 美元付款及供应商延期。不能直接把它当成案例起点；“New chat”不会重置资金。

推荐单独启动一次演示环境，不改动目前 5173 页面和开发数据库。
终端 A（从仓库 tradex/ 开始）：

cd tradex-rag
set -a
source .env
set +a
export TRADEX_DATA_DIR="$(mktemp -d "$PWD/var/five-minute-XXXXXX")"
export TRADEX_TENANT=five-minute-exporter
export TRADEX_RAG_PORT=18770
export TRADEX_RAG_URL=http://127.0.0.1:18770
.venv/bin/python -m uvicorn tradex_rag.api:app --host 127.0.0.1 --port 18770

终端 B（从仓库 tradex/ 开始）：

PORT=5174 TRADEX_RAG_PORT=18770 npm run dev

在新的浏览器私密会话中打开 http://127.0.0.1:5174/，选择 English。
每次从头录制：先停止终端 A 中的演示后端，再执行终端 A 的准备步骤生成新数据目录；关闭旧的私密浏览器会话，再开新的。旧数据库保留，不需要删除。此方案是使用已有环境变量启动隔离实例，未新增一套产品逻辑。

核对基准：
- Available CNY: 128,000。
- Due within 7 days: 160,000。
- TF-26104 供应商日期：October 22。
- TF-26104 预计尾款：USD 12,000，October 29。
- 56-day peak shortfall: CNY 32,000。

预先上传 preload/ 的三个文件；公司现金表选择 Company-wide，订单和供应商条款选择 TF-26104。等待 Searchable，再回 Overview。资料上传是知识检索，不是自动导入会计账本；此案例资料与内置现金表一致。
不要提前上传 presenter-only/ 和 optional-after-demo/ 文件，否则金额、日期或供应商批准可能被提前检索到。讲稿、提示词、标准答案也不上传。

演示使用虚构企业和演示日期 2026-10-17。所有演示日期固定，不改成录制当天。预期结汇按内置比例，不使用实时汇率。

二、五分钟现场操作

0:00–0:40 首页：企业问题
讲 SCRIPT_EN 第一段，指向三个数：128,000、160,000、32,000。不要从空白聊天框开场。
解释 USD 账户被企业预留给其他境外支出，因此这一轮比较只使用 CNY 经营资金。

0:40–1:30 订单 → 文件 → AI
点击 Harbour Supplies / TF-26104，确认这是目标订单，然后进 Documents 页面。
使用连接知识库的 Upload document 表单，选择 live-upload/04_buyer_partial_payment.eml，订单选择 TF-26104。
等文件 Searchable 后，点击该行 Ask AI。用 PROMPTS_EN 的 Prompt 1 替换自动填入的问题并发送。
不要走订单页面的 Continue with sample / Start demo extraction：该路径包含本地规则演示，本次主线要展示真实 Agent + MCP。
收到结果后点击一个引用，显示原始邮件确实没有金额和日期，然后关闭引用弹窗。

1:30–2:30 人工补充
AI 问题的措辞可以变化，不要求逐字匹配讲稿。
展示 presenter-only/05_buyer_clarification.eml：这是第一封邮件之后收到的新回复，不是第一封邮件原本就有的内容。
金额问题填写 USD 6,000；日期问题填写 2026-10-29，并说明预计 CNY 可用日是财务情景假设。
若只有一个合并问题，在留言中一起填写金额与日期；若问分开的两个问题，分别填写。选择题无合适选项时只留言即可。
剩余 USD 6,000 无日期，不猜测其回款时间。
点击 Continue with my answers，等待显示完整提案。

2:30–3:20 确认 → 订单与看板
核对确认卡片：TF-26104 / USD 6,000 / 2026-10-29。
点击 Confirm and update dashboard。页面会自动发起下一轮资金分析；不要重复发送“重新分析”。
切到 Overview，展示订单已变为部分回款计划、峰值缺口 34,000、CNY 银行余额仍为 128,000。
此时后台 Agent 仍可运行。通过 AI tasks 或同一订单会话返回，保留同一 session。
重要：首次缺口仍是 October 22 的 32,000；34,000 是 56 天内的最大缺口，不要把它讲成 October 22 的缺口。

3:20–4:35 比较行动
等待自动分析完成再发 Prompt 5，避免同一会话同时发两个请求。
比较日期均从原约定的 October 22 起算：10 天 → November 1；26 天 → November 17。
预期结果：
- 不延期：October 22 首次缺口 32,000；最大 34,000。
- 延期 10 天：November 6 首次及最大缺口 34,000。
- 延期 26 天：该 CNY 日终预测无负余额，最低余额 48,000。
前提是公司另一笔 November 16 的 120,000 预计回款准时到账，延期暂按无额外费用比较。
这里展示的是情景结果和协商草稿，不能把方案当作已批准安排。首页继续保留当前已确认付款日和缺口，逻辑上是正确的。
若草稿已通过工具保存、界面未展开全文，可指向回答中的请求内容与 activity 中的 Preparing an action draft；不要声称邮件已发送。

4:35–5:00 收束
停留在同一会话的比较结果上，按讲稿结尾说明：邮件理解 → 追问 → 人工确认 → 数值计算 → 行动建议。
不要最后再开融资、政策搜索、沙盒、第二笔订单和通知设置；它们放 Q&A，避免五分钟变成菜单巡游。

三、排练与时间控制
SCRIPT_EN 的时间窗包含讲解、点击和等待；不要为了卡点在回答未完成时朗读一个尚未显示的结果。
先各计时一次：邮件索引、第一轮解读、澄清续跑、确认后的自动分析、最后的情景比较。排练会实际调用当前配置的模型和 embedding API，产生正常用量；本资料包生成时未进行付费模型演练。
如果 5 分钟无法容纳真实延迟，优先录制一次完整实操，压缩纯等待并标注等待加速；不要用预写文本替换失败的 Agent 回答。现场可用同一次录屏作备份。
可压缩：引用弹窗 5 秒；活动日志 5 秒；语言只在开始设置一次。
必须保留：缺项追问、实际回答、确认字段、资金变动、10 天仍不足的比较。
若关键回答失败：显示当前状态，切换到已准备的真实演示录屏；没有录屏时诚实说明需重新运行，不假称成功。

四、可选后续练习（不计入主讲五分钟）
optional-after-demo/07_supplier_acceptance.eml 是供应商之后同意 November 17 的虚构回信。
目前 Agent 的自动确认入口支持客户回款提案，不支持通过该邮件自动提交供应商延期。订单里的 supplier-extension 工作流支持人工核对日期并确认，但提取属于模板演示；务必手工改为 2026-11-17，并如实说明这一点。
这部分若将来接入真实延期提案工具，可作为“协商草稿 → 供应商确认 → 看板缺口归零”的后续产品演示。主片不依赖它。

五、常见问题
为什么不用现有软件？
本例强调跨邮件、缺项确认、现金计算与决策的衔接，不声称 ERP 不能对账或计算现金流。
为什么用 AI？
从非结构化邮件识别变更与不明确之处，并结合用户补充组织下一步；算术仍由代码执行。
为什么 multi-agent？
对账角色解释证据，现金流角色调用计算工具，决策角色比较行动；主助手统一上下文与问题。
为什么不是直接借钱？
先识别真实时间缺口，再比较可协商安排。借款条件、成本和到账日期未确认，不能凭空当作可用资金。
为什么 17 November 没缺口但不是保证？
它依赖其他预测回款、无额外费用的比较假设，以及供应商接受；目前只是条件方案。
